## 0. 最初的思路

- 把工作分为三块：模型选型与部署（可能包括量化、微调、剪枝）、agent 设计（tool calling
  和提示词）、RAG（检索增强生成）
- 选一个基线分数较低的模型，给 agent 留出提升空间，但又不能太低，以免加上 agent 后通过率
  也上不去
- agent 需要能从题面、Vivado 日志等结构化文本中截取有用内容的工具；要确定工作方式
  （ReAct、先规划后执行等）；要设计系统提示词和技能
- agent 设计和 RAG 都与模型强相关，所以先做实验选定模型，再做后续工作
- agent 设计需要阅读论文，借鉴已有方法；RAG 还没有成型的想法

## 1. 总体评价

方向大体正确，有三点建议调整：

1. **三块划分漏了最重要的一块：评测和实验体系。** 模型选型、agent 迭代、失败分析（工程
   质量分的评定重点，`README.md`「提交要求」第 3 条）都要靠它，应该最先做。
2. **「选基线低的模型」方向对，但标准要改。** 真正该看的是「agent 能把这个模型抬到多高」，
   而不是「基线有多低」，见第 2 节。
3. **RAG 在本赛题中收益小，还有违规风险。** 建议降到最低优先级，改成更轻的做法，见第 4 节。

另外，「agent 设计与模型强相关」这点只有部分成立：确定性检查、验证流程、工作流结构基本
与模型无关，只有提示词和工具调用格式需要随模型调整。所以不必等模型完全定下来才开始做
agent。

## 2. 模型选型：先把评分公式算清楚

去掉工程质量项，能由运行数据直接算出的得分为（`SCORING.md` 第 3.1–3.3 节）：

```
得分 ≈ 30·S_a + 40·min(1, ln(S_a/S_b) / ln M) + 墙钟分
S_a = 方案题集得分，S_b = 基线题集得分，M = 满分线倍数
```

M 赛前才公布。下表按 `SCORING.md` 第 4.3 节示例中的 M = 2.5 计算，**S_a、S_b 都是假设值，
不是实测数据**：

| 模型类型 | S_b | S_a | 增益 | 增益分 | 能力分 | 合计 |
| --- | --- | --- | --- | --- | --- | --- |
| 强模型 | 0.60 | 0.85 | 1.42 倍 | 15.2 | 25.5 | 40.7 |
| 中等模型 | 0.35 | 0.75 | 2.14 倍 | 33.3 | 22.5 | 55.8 |
| 中等模型，增益恰好到满分线 | 0.30 | 0.75 | 2.50 倍 | 40.0 | 22.5 | 62.5 |
| 弱模型 | 0.15 | 0.35 | 2.33 倍 | 37.0 | 10.5 | 47.5 |

由此得出：

- **增益到满分线之前，基线每减半，大约多拿 30 分**（40 × ln2 / ln2.5）。「基线要低」
  这个直觉在数学上成立。
- **增益一旦到满分线，再降基线就没有用了**，之后只剩能力分（S_a 每提高 0.1 得 3 分）。
- 所以目标是：**在满足 `S_b ≤ S_a / M` 的前提下，让 S_a 尽量高**。弱模型的问题在于 S_a
  上不去，因为 agent 靠反馈修错，模型必须能看懂错误信息、能按要求改代码。

**选型标准：** 对每个候选模型同时测出 S_b 和「固定探针 agent（一个不再改动、专门用来比较
模型的简单 agent）」下的 S_a，代入上式比较，不能只测基线。

### 2.1 容易忽略的因素

- **思考模式和输出截断。** `baseline.py` 固定 `MAX_TOKENS = 8192`，只使用 OpenAI 标准
  字段，因此服务端默认的 chat template 决定了基线是否开启思考。思考过长的模型在基线里
  可能被截断，直接得 L0（未通过）；agent 可以自己控制思考长度。这是正常的工程选择，但
  必须如实测量，并在报告中如实说明。
- **墙钟分（10 分），以及超时按 L0 计**（`docs/API_CONTRACT.md`）。agent 要多次调用模型，
  模型速度的影响会成倍放大。MoE（混合专家）模型，例如总参数约 30B、每次只激活约 3B 的
  那类，在 32 GB 显存下速度优势明显。
- **ROCm / gfx1201 兼容性是硬性门槛**（决赛硬件，`SCORING.md` 第 1.1 节）。先查清各量化
  格式（AWQ、GPTQ、FP8）在 RDNA4 上有没有可用的实现。`example/serve/README.md` 已经提到
  FP8 被悄悄转成 FP32 的问题。
- **VerilogEval 可能已在模型训练数据中**（`SCORING.md` 第 2.10 条），模型在它上面的分数
  偏乐观，而评测题集中还有未公开的题。建议另外准备一份留出集（开发中不用来调参、只用来
  检查的题目），例如 RTLLM 2.0、CVDP 中的部分题目，或自己编写十几道，用来检查方案是否
  只适应了 VerilogEval。

### 2.2 量化、微调、剪枝

- **量化**只是部署问题（装进 32 GB、提高速度），在选型实验中作为一个维度一起测即可。
- **剪枝**不建议做，收益低、风险高。
- **微调**现阶段不建议做：权重必须开源（`SCORING.md` 第 2.5 条），工作量大；而且**微调
  同样会抬高基线**，除非专门训练工具使用和修错能力，否则可能反而压低增益。可以把现成的
  硬件专用模型（CodeV-R1、VeriThoughts、RTLCoder 等）直接放进候选名单一起测。

## 3. agent 设计：重点是 L1 到 L2

### 3.1 分数在哪里丢

| 丢分环节 | 分值差 | 对策 |
| --- | --- | --- |
| L0：模块名、端口名写错 | 0 分，而功能写错至少有 0.2 分 | **确定性脚本**。评测题集中 `interface` 为空串，要从题面中解析端口表（`docs/API_CONTRACT.md`）。现有 `check_interface` 已有雏形 |
| **L1 到 L2：功能错误** | **0.5，分级表中最大的一级** | **自我验证**，见 3.2 |
| L2 到 L3：综合失败（锁存器、`initial` 语句、不可综合写法等） | 0.3 | 跑一次 synth，再配一份常见问题清单 |

L1 为可编译，L2 为仿真结果与参考实现逐拍一致，L3 为可综合（`README.md`「技术要求」）。

从 Vivado 日志截取有用内容的工具值得做，但只是小改进：xvlog、xelab 的报错本来就短，按
消息编号（如 `[VRFC 10-xxxx]`、`[Synth 8-xxxx]`）提取即可。**主要精力应放在 L2。**

### 3.2 提高 L2 的做法（按性价比排序）

1. **多份候选代码做差分仿真，再投票。** 对中小模型可能是最有效的单项手段。一次并行生成
   N 份候选，在 vLLM 的批处理下墙钟增加有限。用同一组随机激励让 xsim 跑每份候选，按输出
   波形分组，选人数最多的一组。不需要参考答案，也不要求模型写出正确的测试台。思路来自
   CodeT 和 AlphaCode 的聚类方法。
2. **模型根据题面写测试台或参考模型，用 xsim 自测。** 让模型写 SystemVerilog 测试台，或写
   Python 参考模型再与 xsim 输出比对。难点是测试台自己也可能写错，需要交叉校验，例如与
   第 1 种做法结合。
3. **按题型组织的技能包。** VerilogEval 类题目的失败集中在几类：同步或异步复位、卡诺图和
   真值表、状态机、根据波形表推导逻辑、时序差一拍。每类写一份检查清单和提示，按题型注入。
4. **修复策略。** 现有代码每轮都从头重新生成。「在上一版基础上修改」和「重新生成」哪个
   更好，要按失败类别分别测出来。

### 3.3 工作方式：先用固定流程，不急于上自由 ReAct

对本地中小模型，自由形式的 ReAct 加 tool calling 容易出现格式错误、循环、浪费轮次，
而格式错误和超时都直接算 L0。建议流程由脚本控制，只在固定节点调用模型：

```
解析端口（脚本）→ 识别题型（模型或规则）→ 生成 N 份候选（模型，附题型技能）
→ 接口检查和 lint（脚本）→ 差分仿真或自测（xsim）→ 选出结果或针对性修复（模型）
→ synth（脚本）
```

这与 Agentless 论文和 Anthropic《Building Effective Agents》中「能用固定流程就不用
自主 agent」的观点一致。模型确定、分数稳定之后，再在局部（例如修复环节）试 ReAct。

## 4. RAG：基本不做，改成按错误查表

RAG 的做法是把知识库切成小段并建索引（向量或 BM25 关键词索引），提问时找出最相关的
几段拼进提示词，适合「模型不知道、知识库里有」的情况。在本赛题中有三个问题：

1. **规则限制。** 禁止外部检索，本地知识库也**不能包含答案**。用 VerilogEval 参考实现做
   检索库会被认定为硬编码答案，成绩作废（`SCORING.md` 第 2.9、2.10 条），而且对没见过
   的题也没用。
2. **模型缺少的知识很少。** 真正要补的是 Vivado 特有的报错及修法、xvlog 与 iverilog 的
   差异、可综合性问题。这些只有几十条，按错误编号用关键词或正则查表就能准确找到，不需要
   向量检索；嵌入模型还会额外占显存、增加依赖。
3. **现有代码已有一个简单的检索器。** `agent/prompts/skills.py` 中的
   `select(skills, prompt, last_log)` 按错误日志挑选技能，做好它就相当于轻量的 RAG。

值得做的替代方案：

- **错误编号到修复建议的对照表**，从自己跑出的失败日志中整理。RTLFixer 论文表明这类检索
  对修复语法错误很有效。
- **按题型挑选少量示例**：自己编写各题型的示范题（与评测题**不同源**），按题型挑一两个
  放进提示词。有一定价值，放到后期再试。

## 5. 推进顺序

| 阶段 | 内容 | 产出 |
| --- | --- | --- |
| 0. 评测体系（最先做） | 跑通 VerilogEval 156 题和留出集；每题记录级别、失败类别、耗时、token 数、是否截断；自动汇总成表 | `../experiments/` 中可复现的跑分记录 |
| 1. 模型选型（1–2 周，到期必须定下来） | 5–8 个候选只跑基线（每题一次调用，成本低）；选 3 个跑固定探针 agent；代入第 2 节公式比较，选定模型 | `../decisions/0002-model-choice.md` |
| 2. agent 主体 | 端口解析 → 差分仿真投票 → 题型技能 → 修复策略，每一步单独测出提升了多少 | 每一步一份跑分记录 |
| 3. 速度与稳定性 | 调整推理服务配置、并行采样、超时保护、连续数百次请求的稳定性测试 | 墙钟分，避免超时算 L0 |
| 4. 设计报告 | 失败分析是重点，材料从阶段 0 起积累在 `../failures/` | `../../REPORT.md` |

阶段 1 和阶段 2 可以部分并行：端口解析、日志提取、差分仿真框架都与模型无关，可以先做。
