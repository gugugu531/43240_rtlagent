## 1. 先把取舍标准写清楚

### 1.1 选型要最大化的东西

由 `SCORING.md` 第 3.1–3.3 节，能由运行数据直接算出的分数是：

```
总分 ≈ 30·S_a + 40·min(1, ln(S_a/S_b)/ln M) + 墙钟分
S_a = 方案（agent + 技能包）题集得分
S_b = 同一模型、无 agent、单次直接生成的题集得分（赛事方 baseline.py 产出，我们不得改动）
M   = 满分线倍数，赛前公布
```

`docs/FAQ.md` Q14 把这个取舍说得很直白：「选用能力更强的模型不会直接转化为更高的总分。」

两个方向都是单调的，但**互相冲突**：

- `S_b` 越低越好——它是分母，而且越低增益越容易做大
- `S_a` 越高越好——它同时进入能力项（系数 30）和增益项的分子

问题在于 `S_b` 和 `S_a` 出自同一个模型。所以**只测基线排不出序**，必须对每个候选同时测出
`S_b` 和「同一个冻结的 probe agent 下的 `S_a`」。

### 1.2 一个反直觉但很重要的推论

`S_b` 是用赛事方那份**单次直接生成、temperature 0、不重试、不调用工具**的脚本测的。
也就是说，`S_b` 高不完全是好事——它衡量的是「一次性裸跑有多强」，而这部分能力**本来就已经
被算进分母，无法再转化为增益**。

由此得出本轮的选型倾向：

> **要的是「一次性裸跑一般、但能看懂报错并改对」的模型，不是「一次性裸跑最强」的模型。**

RTL 专用小模型（例如 CodeV-R1-7B）恰好是前者的反面：它的全部卖点就是一次性裸跑得分高
（论文报告 VerilogEval v2 pass@1 68.6%，见 <https://arxiv.org/abs/2505.24183>），
按上面的公式，它的 `S_b` 越高、增益空间越小。**这类模型要测，但定位是对照组，不是首选。**

反过来，`S_a` 这一侧的天花板并不低：有工作用「验证台反馈 + 进化搜索」的 agent 把
VerilogEval 2.0 的 pass@1 做到 97.5%（COEVO，<https://arxiv.org/abs/2604.15001>，
注意它用的是商用模型和 Icarus/Yosys 判定，不能直接类推到我们的条件）。所以真正的瓶颈不是
「模型能写多好」，而是**「模型能不能被 agent 抬起来」**——这一点只能实测。

### 1.3 用假设数字看一眼量级

下表只用来说明趋势，`S_a`、`S_b` 都是假设值（M 取 2.5，墙钟与工程质量项不计）：

| S_b | S_a | 增益 | 能力分 | 增益分 | 合计 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0.20 | 0.55 | 2.75 | 16.5 | 40.0（封顶） | **56.5** |
| 0.20 | 0.70 | 3.50 | 21.0 | 40.0（封顶） | **61.0** |
| 0.42 | 0.70 | 1.67 | 21.0 | 22.3 | 43.3 |
| 0.42 | 0.85 | 2.02 | 25.5 | 30.8 | 56.3 |
| 0.49 | 0.85 | 1.73 | 25.5 | 24.1 | 49.6 |
| 0.62 | 0.90 | 1.45 | 27.0 | 16.3 | 43.3 |
| 0.69 | 0.95 | 1.38 | 28.5 | 14.0 | 42.5 |

（`增益分 = 40 × ln(增益)/ln(2.5)`）

读法：**基线 0.20 的弱模型只要能被 agent 抬到 0.50，就已经拿满增益分**；而基线 0.69 的强模型
即使做到 0.95，总分也只有 42 分左右。这解释了为什么小模型要当成正经候选来测，而不是
顺手带一个。

### 1.4 低基线有两个风险，必须一起看

1. **`S_b` 接近 0 时增益无从计算。** `SCORING.md` 第 3.2 节：「基线得分为零时，增益无从计算，
   本项按赛前公告的规则单独处理。」规则未知，等于把 40 分押在一个看不懂的条款上。例如
   `gpt-oss-20b` 这类思考模型，思考 token 占满 `baseline.py` 固定的 8192 上限就会输出空内容
   （`example/baseline.py` 第 128–132 行的注释记录了这一点），`S_b` 可能直接掉到 0。
2. **能力项 30 分跟着一起低。** 小模型 `S_a` 上不去时，两边都丢。

### 1.5 M 未知，所以要看稳健性

M（满分线倍数）赛前才公布，`SCORING.md` 第 4.3 节的示例用 2.5。选型时对 M = 2.0 / 2.5 / 3.0
各算一遍，取「最坏情况下最好」的那个模型，而不是押一个 M。

## 2. 硬门槛（不满足直接排除）

| 门槛 | 说明 |
| --- | --- |
| 单卡 32 GB | `SCORING.md` 第 1.3、2.2 节；实测显存采样，超限的运行不计入统计 |
| 决赛硬件可用 | 决赛是 R9700（gfx1201），验证阶段的 W7900（gfx1100）是上一代，**两边的能力不对等**：vLLM 的 `supports_fp8()` 在 gfx1201 上为真、在 gfx1100 上为假。FP8 在开发机上根本起不来，只能在目标卡上验证。详见 §2.1 |
| 开源权重、可离线 | 断网沙箱内运行，不下载任何东西 |
| OpenAI 兼容接口 | `baseline.py` 只调 `/v1/chat/completions`，不带身份验证头 |
| 速度够快 | agent 每题要调好几次模型；模型慢会直接吃掉轮数和墙钟分 |
| 许可证 | 须能公开下载与再分发；注意部分「非商用」许可 |

另外三条来自已有实测（`archive/2026-09-24-baseline-sweep.md`）：

- 32B AWQ 模型实测显存 33.7–34.1 GB，**已超 32 GB**，除非量化档位降下来，否则出局
- 这张卡上 AWQ 很慢（约 4 token/秒/路），GPTQ 与 MoE 反而快
- Qwen3 系列混合思考模型必须加 `--reasoning-parser qwen3`，否则思考内容混进正文

### 2.1 服务栈本身也可能卡住，这是本轮最大的技术风险

这一节是专门调研量化格式与 ROCm 支持后补的，结论直接改变了后面的实验设计。

**官方支持表不能当成「能不能跑」的答案。** vLLM 文档里 AMD 一列只勾了 FP8 W8A8 和 GGUF，
AWQ、GPTQ、Marlin、INT8 全标不支持（[支持表](https://github.com/vllm-project/vllm/blob/main/docs/features/quantization/README.md)）。
但已合并的改动表明 AWQ/GPTQ 在 RDNA 上确实能跑，其中
[PR #31715](https://github.com/vllm-project/vllm/pull/31715)（2026-01-15 合并）修掉了
**量化模型在 gfx1201 上加载直接崩溃**的问题（`Unknown GPU architecture: gfx1201`）。
**Marlin 系列在 ROCm 上确实不可用**，会自动退到 `MoeWNA16Method`。

**开发机和目标卡的能力不对等**（这条最影响安排）：

| | gfx1100（W7900，开发用） | gfx1201（R9700，决赛用） |
| --- | --- | --- |
| BF16 / FP16 | 原生 | 原生 |
| FP8 W8A8（dense） | ❌ `supports_fp8()` 为假，不加补丁直接报 `NotImplementedError` | ✅ 原生 FP8 WMMA |
| FP8 MoE | ❌ | ❌，要靠未合并的 [PR #36659](https://github.com/vllm-project/vllm/pull/36659)，否则退回 BF16 计算 |
| AWQ / GPTQ Int4 | ✅ 已报告可用 | 加载已修好，**性能未经验证** |
| MXFP4 | 非原生 | 非原生（`supports_mx()` 只认 gfx95/gfx1250） |

结论：**FP8 这一档在 W7900 上做不了实验**，只能在 R9700 上补；而 R9700 上 MoE 相关的每条路
（AWQ MoE 性能、GPTQ MoE、FP8 MoE、MXFP4）目前都是「未验证」。

**顺带更正仓库里的一处说法。** `example/serve/README.md`「跨代架构的已知问题」第 2 条说
FP8 权重会被静默反量化成 FP32。这个说法的最初报告者已经自己更正
（[issue #28649](https://github.com/vllm-project/vllm/issues/28649)：那批性能提升主要来自
cuda graph 改进，不是 FP8 补丁）。那条退化路径在代码里确实存在，但**在当前版本上没有复现证据**。
我们按「未证实」处理：既不拿它当排除 FP8 的理由，也不拿它当 FP8 一定能用的理由。

**兜底方案是 GGUF + llama.cpp**：gfx1201 可以编译运行（`-DGGML_HIP=ON -DGPU_TARGETS=gfx1201`，
[PR #26745](https://github.com/ggml-org/llama.cpp/pull/26745) 的文档补充还没合并），
Q5_K_M/Q6_K 比 Q3_K_S 更适合 RDNA4。但它只能作为兜底，**方案和基线必须用同一个服务**，
不能一个走 vLLM、一个走 llama.cpp（前缀缓存和上下文处理不同，比值没有意义）。

**RTL 专用模型的调研结论**（避免重复劳动，这里把整类模型一次说清）：

- **值得占一个槽位的只有两个**：`CodeV-R1-RL-Qwen-7B`（唯一在 VerilogEval v2
  spec-to-RTL 上有大分差、且版本口径明确的模型，Apache-2.0、完整权重），以及
  `nyu-dice-lab/VeriThoughts-Reasoning-14B`（VerilogEval-Human **v1** pass@1 只有 43.7%，
  但训练数据来源最透明；只在将来需要自己微调时才优先考虑）。
- **不用测**：`ishorn5/RTLCoder-Deepseek-v1.1`（v1 时代、权重只有 `.bin`）、
  `shailja/fine-tuned-codegen-*-Verilog`（2023 年，查不到权威 VerilogEval 分数）、
  `henryen/OriGen`（VerilogEval-Human v1 有 54.4%，但**只发布了 LoRA 适配器**，基座是
  GPL-3.0，提交时合并与许可都麻烦）、`chipcraftx-io/chipcraftx-rtlgen-7b`
  （**CC-BY-NC-4.0 非商用许可**，训练数据未公开，宣传的 98.7% 其实是它加 Claude 的混合系统成绩）。
- **查无权重**：ChipNeMo、AutoChip、VerilogCoder、CraftRTL、HDLGen、MEV-LLM 都只有论文或框架。
  另外 **OriGen-32B 不存在**，只有 7B 的 LoRA 对。
- **一个必须记住的前提**：跨论文的 VerilogEval 分数不可直接比较（提示词写法、判定器、
  是否下发测试台都会改变分数，VerilogEval 原论文自己就警告过这点）。所有对外部分数的引用
  只用于决定「值不值得占一个槽位」，最终一律以我们在 `tasks/` 上实测的 `S_b`、`S_a` 为准。

**量化格式上必须先排除掉的东西**（这条能省很多冤枉时间）：

- **NVFP4 不能用。** 2026 年的量化版本里 NVFP4 占了大多数（`nvidia/*-NVFP4`、
  `RedHatAI/*-NVFP4`），但它是面向 NVIDIA Blackwell 的格式，查不到任何 ROCm/RDNA4 可用的证据。
  AMD 机器上只用 **FP8、AWQ、GPTQ、GGUF** 四种。
- **≥27B 的模型不要指望 FP8。** `Qwen3.6-35B-A3B-FP8` 是 36.0 GB，连加载都过不去；
  `GLM-4.7-Flash` 31.2 GB 也留不下 KV 空间。这个量级只能走 INT4。
- **优先用 AMD 自己发布的量化版本**（HF 上 `amd/` 作者下，例如
  `amd/gpt-oss-20b-MoE-Quant-W-MXFP4-A-FP8-KV-FP8`、`amd/granite-4.0-h-small-w4a16-llmcompressor`）。
  它们是最可能在这张卡上跑通的artifact，但「存在」不等于「gfx1201 上验证过」。
- **注意需要授权（gated）的仓库**：`meta-llama/*`、`google/gemma-3-*` 需要先在网页上同意许可，
  `mistralai/Codestral-25.01`、`01-ai/Yi-Coder-34B-Chat` 等连参数量都查不到（HTTP 401）。
  断网沙箱里没有网页可点，这类权重要么提前下好，要么别选。Gemma 4 已经改成普通的
  Apache-2.0，没有这个问题。

## 4. 同一个模型的不同量化精度：怎么测

`docs/FAQ.md` Q13 明确把「在同等显存条件下如何在参数量与量化精度之间取舍」列为赛道的考察点，
所以这一节不只是调优，也是要写进报告的内容。

### 4.1 要测的不是「量化会不会掉分」，而是净效果

这个赛题的特殊之处：**量化同时改变分子和分母**。方案和基线用的是同一份权重
（`docs/FAQ.md` Q18：不绕过的部分是推理服务，即同一模型、同一量化方式与同一份上下文配置）。
所以降精度会同时压低 `S_a` 和 `S_b`，增益未必变差，但能力项一定跟着掉。

由此三条假设，需要数据判定：

| 假设 | 如果成立，结论 |
| --- | --- |
| H1：量化对**单次裸跑**的伤害 ≥ 对**多轮修复**的伤害 | 低精度反而提高增益，值得用 4-bit 换速度 |
| H2：量化主要伤害**看懂报错 / 遵循格式**的能力 | 高精度更好，因为 `S_a` 掉得比 `S_b` 快 |
| H3：低精度换来更多轮数，抵消掉精度损失 | 按总时间预算选，而不是按单次质量选 |

**外部已有的证据**（一篇专门测「量化对代码生成的影响」的工作，
<https://arxiv.org/abs/2607.14181>，4-bit 权重量化、pass@1）：

- **4-bit 大体保得住功能正确性。** 对 Qwen2.5-Coder-7B，AWQ 在两个基准上与全精度**完全相同**
  （McEval-Java 0.45→0.45，BigCodeBench 0.41→0.41）。
- **GPTQ 方差很大，不能假设它中性。** 同一个 Qwen2.5-Coder-7B，GPTQ 在一个基准上掉到 0.32
  （−13 个百分点），在另一个基准上不掉。
- **QuIP# 明确有害**（0.45→0.32、0.23→0.12），直接排除。
- ⚠️ 这篇工作的题量很小（42–190 题），个位数差异在噪声里，只有大摆动可信。

因此本轮的默认选择是：**优先 AWQ，GPTQ 必须实测，不用 QuIP#，FP8 只在目标卡上验证。**

### 4.2 量化实验矩阵

| 组 | 模型 | 档位 | 想隔离的变量 |
| --- | --- | --- | --- |
| 量化对照组 1（干净对照） | `CodeV-R1-RL-Qwen-7B` 或 `Qwen3.5-9B`（BF16 装得下） | BF16 vs AWQ-4bit | 纯量化影响。同一模型、同一尺寸，只有精度变 |
| 量化对照组 2（实际可用档） | `Qwen3.6-35B-A3B`（BF16 装不下） | AWQ-4bit vs GPTQ-4bit | 32 GB 下真实可选的档位之间差多少。按 §4.1 的证据，预期 AWQ 更快也更稳，GPTQ 要实测 |
| 量化对照组 3（中间档） | `Qwen3.6-27B` | AWQ-4bit vs AWQ-6bit | 「降参数量」和「降精度」谁更划算 |

**FP8 这一档在验证阶段做不了**：W7900 上 `supports_fp8()` 为假（§2.1），只能在拿到 R9700
之后再补。所以本轮的量化结论要写成「W7900 上得到什么、哪些必须在目标卡上复验」两部分。

可选补充：对 量化对照组 1 里的 7B 模型，用 llama.cpp 走 GGUF（Q4_K_M / Q6_K / Q8_0）与 vLLM 的
AWQ 对比。注意后端不同会同时改变速度和数值行为，只能作为参考，不能和 vLLM 的结果混在一张表里比。

### 4.3 每一档都要记录的字段

指标清单见 §5；量化实验至少要留下 `S_b`、`S_a`、单路速度、显存峰值、截断率这几项，
否则事后无法解释「为什么这一档更好」。

## 5. 评估指标

指标分四类：**门槛**（不过就出局）、**质量**（baseline 得分与停留阶段）、
**资源与速度**（显存、KV Cache、tps、单题耗时）、**其他情况与错因**。
`S_a`、增益、可计算分不在筛选阶段，见 §6.2。

### 5.1 门槛指标（不通过就出局，不打分）

| 指标 | 判据 | 怎么测 |
| --- | --- | --- |
| 单卡显存峰值 | **≤ 32 GB**（`SCORING.md` 第 1.3、2.2 节，硬性） | `rocm-smi` 按秒采样整个跑分过程取峰值，不能只量加载后那一瞬间 |
| 服务可用 | `/v1/models` 与 `/v1/chat/completions` 都正常 | 与 `baseline.py` 的调用方式一致（不带 `Authorization` 头） |
| 断网可加载 | 断掉出口后仍能启动服务并生成 | 提交是断网沙箱，权重和依赖必须预先就位 |
| **目标卡可用** | 在 gfx1201 上重复「加载 + 一次生成」 | 开发卡（gfx1100）上的结论不算数，见 §2.1 |
| 许可证与可获取性 | 许可允许再分发、不需要网页点同意 | gated 仓库在断网沙箱里是死路，见 §3 |

### 5.2 baseline 得分与停留阶段（筛选阶段的核心质量指标）

| 指标 | 定义 |
| --- | --- |
| **可综合率** | L3 题数 ÷ 题数 |
| **功能正确率** | (L2 + L3) 题数 ÷ 题数。**与上一项分开记**，因为 L1→L2 的系数差 0.5 是全表最大的一级 |
| **题集得分 `S_b`** | Σ每题系数 ÷ 题数，系数 L0/L1/L2/L3 = 0 / 0.2 / 0.7 / 1.0 |
| **停留阶段分布** | L0 / L1 / L2 / L3 各多少题 |
| **停在 L0 的细分** | `syntax` / `interface` / `elab` / `truncated` / `empty_reply` / `timeout` 各多少题 |
| 截断导致的 L0 | trace 里 `finish=length` 且最终没产出代码的题数。`baseline.py` 固定 `max_tokens=8192`，思考类模型容易撞这个上限 |

口径：基线条件不可改（temperature 0、单次、不重试、不调用工具，`SCORING.md` 第 3.2 节）。
筛选阶段只跑 baseline，所以这一节的数字就是 `S_b`。

### 5.3 KV Cache 显存（细化）

**先估算。** KV 的字节数 = `2`（K 和 V）× Σ各层(`kv_heads × head_dim`) × dtype 字节数 × token 数。
三类层要分开算：

- **全注意力层**：随 token 数线性增长
- **滑动窗口层**：封顶在窗口长度，不再增长
- **线性注意力层**：不产生 KV，只有固定大小的状态（Qwen3.5 / 3.6 / 3.8 的 `qwen3_5` 结构里占 3/4 的层）

按各候选 `config.json`（2026-09-25 实拉）算出的理论值，bf16 KV、**单个序列**、32k 上下文：

| 模型 | 全注意力层 / 总层数 | kv_heads × head_dim | KV @ 32k |
| --- | --- | --- | ---: |
| Qwen3.6-35B-A3B | 10 / 40（其余为线性注意力） | 2 × 256 | ~0.64 GB |
| Qwen3.5-35B-A3B | 10 / 40 | 2 × 256 | ~0.64 GB |
| Qwen3.5-9B | 8 / 32 | 4 × 256 | ~1.0 GB |
| Qwen3.5-4B | 8 / 32 | 4 × 256 | ~1.0 GB |
| Qwen3.8-27B | 16 / 64 | 4 × 256 | ~2.0 GB |
| Qwen3-Coder-30B-A3B | 48 / 48（全部是全注意力） | 4 × 128 | ~3.0 GB |
| Qwen3-30B-A3B-Instruct-2507 | 48 / 48 | 4 × 128 | ~3.0 GB |
| North-Mini-Code-1.0 | 13 / 49，另 36 层窗口 4096 | 4 × 128 | ~1.1 GB |
| gpt-oss-20b | 12 / 24，另 12 层窗口 128 | 8 × 64 | ~0.77 GB |
| CodeV-R1-RL-Qwen-7B（Qwen2.5） | 28 / 28 | 4 × 128 | ~1.75 GB |

**这张表最重要的结论：32k 上下文下单序列 KV 只有 0.6–3 GB，不是 32 GB 预算的瓶颈，权重才是。**
所以 KV 这一项的意义不是"省显存"，而是三件事：能开多大并发、能给 activation 与框架留多少余量、
以及最长的题会不会因为池子不够而失败。

**必须实测，不能只按公式算**，两个理由：

1. 滑动窗口和线性注意力要 vLLM 认得 `layer_types` 才会按窗口/状态处理。认不出来就按全注意力
   分配，数字会差 8–30 倍。
2. `qwen3_5` 是很新的结构，当前 vLLM 是否完整支持需要现场确认。

实测用三条互相印证：

1. **vLLM 启动日志**：会打印 KV 池的总 token 数和「某长度下最大并发」——最直接的读数
2. **运行时指标**：`/metrics` 里的 `vllm:kv_cache_usage_perc`（或 `gpu_cache_usage_perc`），
   在一次 32k 长上下文请求前后各读一次
3. **端到端**：一次 32k 请求前后 `rocm-smi` 的差值；这个差值含 activation，只能当上界

要记录的字段：KV dtype（bf16 / fp8）、KV 池总 token 数、32k 单序列占用、prefix caching 是否开启、
`max_model_len` 设定值、实测最大并发。

### 5.4 显存占用（权重与总量）

- `rocm-smi` 按秒采样，记**加载后稳态**与**跑分峰值**两个值（`SCORING.md` 第 2.2 节按运行采样）
- 同时记 vLLM 的 `gpu_memory_utilization` 设定，便于换算到 32 GB 口径
- 分三段记：**权重 / KV 池 / 其余**（activation + 框架）。权重可以直接从模型文件体积读出，
  这样"超没超 32 GB"能立刻归因到哪一段

### 5.5 速度指标：tps 与单题耗时

| 指标 | 口径 | 为什么这样定 |
| --- | --- | --- |
| 平均 tps（并发 1） | 输出 token 数 ÷ 生成耗时，先按题取中位数再平均 | agent 是一条一条串行请求的，并发 4 的聚合吞吐不代表它的实际体验 |
| 平均 tps（并发 4） | 同上，批量口径 | 只用于估批量筛选要多久 |
| 首 token 时间 | 由 trace 的 `elapsed_s` 与 token 数粗估 | 长上下文时它决定墙钟 |
| 平均单题耗时 | `solve.json` 的 `elapsed_s`：均值 / 中位数 / p90 / 最长 | 均值用于排序，**p90 与最长决定超时风险** |
| 综合与 lint 耗时 | trace 里的工具记录 | 分清"模型慢"还是"工具慢"，才知道该优化哪一头 |

口径警告：并行跑分（4 路）的耗时**只能相对比较，不能当墙钟分**。赛事方口径（请求发出到收到响应）
留到联合阶段，用 `dev/tools/remote/submit_client.py` 在独占环境下测。

### 5.6 其他情况（稳定性与格式）

- 输出截断率（`finish=length` 的比例）
- 空回复率、提取失败率（回复里没有代码块）
- 思考内容混进正文的比例（漏加 `reasoning-parser` 时会明显升高）
- 模型请求失败率与超时率（trace 里的 `llm` 记录）
- 权重体积、下载耗时、加载耗时——决定一批能测几个模型（§7.1）
- 长跑稳定性：`submit_client.py --tag soak` 连续投题数百次，观察是否崩、显存是否漂移

### 5.7 主要错因（也是筛选阶段最有信息量的一项）

`dev/tools/analysis/analyze.py` 已经能给每个样本归一类（`syntax` / `sim_mismatch` / `interface` /
`elab` / `synth_fail` / `truncated` / `timeout` / …），并统计 Vivado 报错编号的频次。

筛选阶段要额外回答一个**模型层面**的问题：**错因结构决定它值不值得进联合阶段。**

- 错在 `syntax`、`interface`、`elab`、`truncated` 是**有确定依据可修**的（报错文本、题面端口表、
  服务参数），agent 一般能救回来 → 这类 `S_b` 低是好事
- 错在 `sim_mismatch` 要看题型分布，是 agent 最难救的一类 → 全靠它撑起来的低 `S_b` 是坏事
- 所以「`S_b` 低」本身不能说明问题，**要连着错因一起看**

### 5.8 记录与复现要求

- 原始数据落 `dev/runs/<运行编号>/`，字段见 `../eval/README.md`（每个样本一份
  `solve.json` / `verdict.json` / `judge.log`，外加汇总的 `samples.csv`）
- 每次跑分生成 `dev/docs/experiments/<运行编号>.md`，手工补写「改动与假设」「结论」两节
- 文档里出现的每个得分、耗时、通过率都要注明来自哪次运行（`CONVENTIONS.md` 第 3.4 节）
- **每测完一个模型就往汇总表补一行**：模型 / 量化 / `S_b` / 可综合率 / 功能正确率 /
  停留阶段分布 / 主要错因 / tps(并发1) / 单题耗时中位数与 p90 / 显存峰值 / KV@32k / 下载耗时

### 5.9 两个阶段的排序规则不一样

- **筛选阶段（只有 baseline）**：不是按 `S_b` 从高到低排，而是按
  **「上限分」= `30 + 40·min(1, ln(1/S_b)/ln M)`**（假设 agent 能做到满分时的可计算分）
  排序，再结合 §5.7 的可修错因占比往下筛。理由：`S_b` 越低上限越高，但只有错因可修时这个上限才拿得到。
- **联合阶段（有 agent 结果）**：按 §1.3 的可计算分排序，M 取 2.0 / 2.5 / 3.0，
  选最坏情况下最好的。

噪声量级（判断「分差算不算数」）：`quick` 34 题里一道题从 L0 变 L3 是 `1/34 ≈ 0.029`；
全题集 152 题是 `1/152 ≈ 0.0066`。所以 quick 上小于约 0.06 的差距不要当结论——
这也是筛选阶段直接用全题集的原因之一（§7.2）。

## 6. 怎么测（协议）

### 6.1 固定住的东西

不同模型的分数只有在同一套条件下才能比：

| 项 | 取值 |
| --- | --- |
| 题集 | 先 `quick`（34 题）筛，入围者跑全题集（排除 4 道坏题后 152 题） |
| 判定 | 本机 Vivado 2026.1，`dev/tools/run_eval.py`，与 `selftest/run_selftest.sh` 同口径 |
| 服务参数 | `max_model_len` 32768，`gpu_memory_utilization` 按仿真 32 GB 设定，思考默认关闭，按模型加 `reasoning-parser` |
| 并发 | 求解 4 路、判定 4 路（小机器上判定受 CPU 限制，`../eval/README.md` 有说明） |
| 记录 | 每次跑分生成 `dev/docs/experiments/` 记录，原始文件留在 `dev/runs/` |

为什么连服务参数都要固定：有工作用 26 个开源模型、108 组解码参数做过实验，**同一个模型换解码
参数，pass@1 能差 25.5%，比模型家族之间的平均差距还大**，而且默认参数往往远离最优
（<https://arxiv.org/abs/2604.17102>）。不固定并记录参数，测出来的差异分不清是模型带来的
还是参数带来的。

一个对我们有利的细节：**基线的解码参数由赛事方固定**（`example/baseline.py`：temperature 0、
top_p 1.0、max_tokens 8192、单次、不重试），我们动不了；而 agent 侧的采样参数是我们自己的。
这既是可用的工程空间，也是需要在报告里如实说明的地方（另见 §8 第 3 条）。

### 6.2 两个跑分阶段（按团队决定：先筛选，后联合）

**阶段一 · 模型筛选：只跑 baseline（`--modes baseline`）。**

理由：`baseline.py` 每题只调用模型一次，所以 GPU 时间很短（155 题、4 路并发，求解约 5 分钟），
真正的成本是下载权重和本地判定。省下来的时间用来多测模型更划算。

代价要写清楚：这一阶段**拿不到 `S_a`**，所以排序靠 §5.9 的「上限分 + 可修错因占比」做代理。
这个代理可能失灵——错因看着可修、实际 agent 抬不动的情况一定会出现。对策见 §6.3。

**阶段二 · 联合跑分：入围模型跑 `--modes agent,baseline`。**

分子分母必须出自同一次运行（`SCORING.md` 第 3.2 节、`docs/FAQ.md` Q18），
所以这一步不能拆成两次跑。到了这一步才有 `S_a`、增益和 §1.3 的可计算分。

### 6.3 筛选阶段的代理变量可能失灵，怎么兜

- **入围名额放宽到 4–5 个**，不要只留 2 个。多测一个模型的成本主要是一次下载，
  比赌错模型的代价小。
- 联合阶段**先跑 `quick` 34 题**验证代理变量（可修错因多的模型是不是真的更容易被抬起来），
  确认之后再让前 2–3 名跑全题集。
- 把代理变量失灵的例子记进 `dev/docs/notes/`，这本身就是工程质量项（失败分析）要的材料。

### 6.4 墙钟口径单独测一次

赛事方的代价项按「请求发出到收到响应」计（`SCORING.md` 第 3.3 节），并行跑分数不能替代。
所以在联合阶段对最终入围的模型，用 `dev/tools/remote/submit_client.py` 在独占环境（不并发）下
跑一遍，得到的才是可用于报告的墙钟数。

## 7. 预算与执行顺序

### 7.1 单个候选模型的成本（估）

已有实测：全题集 baseline 一次约 **11 分钟**端到端（其中求解约 5 分钟，其余是本地判定；
`dev/runs/20260924-210547-full-...`）。云端实例还要加上下载权重和加载模型的时间
（`../remote/README.md`：下载 1–20 分钟，按 12–300 MB/s 波动；每次实例销毁后权重清空）。

| 环节 | 全题集 | quick 34 题 |
| --- | --- | --- |
| 下载 + 加载 | 5–25 分钟 | 同左（下载占大头，省不掉） |
| baseline 求解 | ~5 分钟 | ~1 分钟 |
| 本地判定 | ~6 分钟 | ~3 分钟 |

结论：**筛选阶段的成本几乎全在下载上**，因为只跑 baseline。一次 4 小时的会话，
现实一点是 **4–6 个模型**。到了联合阶段，agent 每题要多次生成、还要跑综合，
单个模型的成本会涨到 30–60 分钟，那时一批只能装 2–3 个。

## 8. 还需要你确认的部分

前面三条已经定了（候选清单、指标、先筛选后联合）。下面是我对未指明部分的考虑，
按你的要求写得尽量短，并给出理由。

| 事项 | 我的建议 | 理由 |
| --- | --- | --- |
| 筛选用全题集还是 `quick` | **全题集** | 筛选阶段每题只有一次模型调用，GPU 成本是几分钟；而 `quick` 分数虚高 0.06–0.08，全题集直接给出可决策的绝对值 |
| 量化对照什么时候做 | **入围之后**，但可以顺手对 `Qwen3.6-35B-A3B`（AWQ-4bit） 多测一个档 | 量化同时改变分子分母，只有拿到 agent 结果才能判净效果；顺手多测一档的成本只是一次下载 |
| 要不要跑 pass@5 | **暂不跑**，只对最终 1–2 个模型做 | 5 倍成本、只作诊断、不计入总分，而现在连 `pass@1` 都还没有 |
| 是否保留 probe agent | **不保留**（按你的决定） | 代价是筛选阶段没有 `S_a`，用 §5.9 的代理变量兜，见 §6.3 |
| 「服务默认关思考、agent 单独开思考」 | **两边一致，默认关，并在 `MODEL.md` 与报告里如实写明** | 规则固定的是 `baseline.py` 的提示词与采样参数，服务配置归我们；但让 agent 单独开思考会把分子分母的差距人为拉大，风险大于收益 |
| `M` 未知怎么处理 | **对 M = 2.0 / 2.5 / 3.0 各算一遍，取最坏情况下最好的** | `SCORING.md` 第 4.3 节的示例用 2.5，但真实值赛前才公布 |
| 优先用谁发布的量化版本 | **优先 HF 上 `amd/` 作者下的版本** | 那是 AMD 自己为 ROCm 出的重整版，最可能在这张卡上直接跑通 |
