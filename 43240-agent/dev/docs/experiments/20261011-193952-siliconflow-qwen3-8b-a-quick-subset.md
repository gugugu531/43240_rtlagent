这里存在明显的超时契约问题：Workflow 的 Generate Node 写的是 180 秒，服务配置写的是 300 秒，但实测一次成功
响应耗时 333.7 秒，另一次失败事件耗时也超过 180 秒。说明当前 HTTP 客户端的 timeout 并不是严格的整次请求
墙钟上限，配置的两层超时也没有统一。

并发 4 同时运行 Agent 和 judge 时，本机 Vivado 也发生严重资源竞争：三个最终 L3 的 judge 分别耗时约
352～362 秒，`Prob048` 的内部 lint 接近 300 秒仍未完成。恢复阶段的 4 个并发模型请求则全部在首轮超时。
随后用并发 1 补跑 `Prob062_bugs_mux2`，两次请求在约 340 秒内仍未得到答案，说明当时 SiliconFlow 服务本身
也处于高延迟状态，不能把问题全部归因于本机并发。

## 方案 A 是否真的进行了修复

没有。

- 发生了 2 次 `retry_request`，它们是模型请求超时后的原请求重试，不是依据 lint 反馈修代码。
- 发生了 3 次明确的 lint 失败，但诊断记录里的 `failure_kind` 都是 `unknown`。
- 失败策略对 `unknown` 选择 `stop`，记录中的 `repairs` 始终为 0。
- 因此独立 Feedback Node 和“带证据重新生成候选”的路径仍未被有效验证。

这比单题 smoke 提供了更明确的结论：修复路径不是因为题目都太简单而没有触发，而是已有可修复语法错误时，
错误分类器没有把它们路由到修复 Node。

## 下一步建议

在做 E1/E2 或增加 RAG、规划、Reflexion 之前，先修下面三个基础问题：

1. 把 Vivado 的常见编译错误映射为可修复类别，至少覆盖 `VRFC 10-1280`（过程赋值给 wire）和
   `VRFC 10-9336`（ANSI 端口重复声明），不能再落到 `unknown -> stop`。
2. 统一服务、Generate Node 和整题期限的时间契约，并让请求超时成为真正的墙钟上限。360 秒整题期限下，
   两次 180 秒请求几乎不给 lint、综合和补丁验证留下时间。
3. 本机实验先使用 `solve_jobs=1`、`metric_jobs=1`；模型服务稳定后再分别测并发，避免模型延迟与 Vivado
   资源竞争污染 Agent 能力数据。

修好后先跑一个真正均衡的 8～12 题小集合，每个类别至少一题，并确认至少一题出现
“lint 失败 → 结构化反馈 → 第二个候选 → 重新检查”。达到这个条件后，再跑完整 34 题 quick，并开始 E1/E2。
