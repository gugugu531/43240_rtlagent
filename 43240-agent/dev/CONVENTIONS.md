# 开发规范

本文是团队的开发约定，包括目录组织、文档写作、提交与分支管理、代码约定。第 1 节「合规红线」
来自比赛规则，违反会导致丢分甚至成绩作废，其余各节是团队内部约定。

规范本身也可以修改：发现不合适的地方，在分支上修改本文，并在 PR（Pull Request，合并请求，见 4.3 节）中说明理由。

---

## 1. 合规红线

| 规则 | 违反的后果 | 依据（仓库根目录下） |
| --- | --- | --- |
| 不修改 `baseline.py` 和 `run_baseline.sh` | 增益项 40 分不得分 | `SCORING.md` 第 2.4、3.2 节 |
| 参考答案、题目的正确解只能放在 `dev/`，不能出现在 `agent/`、`skill/`、提示词或其他提交文件中 | 该赛道成绩作废 | `SCORING.md` 第 2.9、2.10 条 |
| 方案运行时不能联网、不能下载任何东西；依赖和模型权重都要预先放进镜像 | 全部运行得分无法产生 | `SCORING.md` 第 2.1、2.3 条 |
| 提交的模型必须是本地部署的开源权重，不能是商用 API | 同上 | `SCORING.md` 第 2.12 条 |
| 提交目录中的目录名和文件名只用英文小写字母、数字、下划线或连字符 | 不符合提交要求 | `README.md`「提交要求」 |
| 不把 API key、令牌、`remote.env`、`selftest/env.sh` 提交到 git | 泄露密钥 | — |

检查 `baseline.py` 是否被改动：

```bash
diff example/baseline.py 43240-agent/baseline.py && diff example/run_baseline.sh 43240-agent/run_baseline.sh
```

## 2. 目录组织

### 2.1 各目录的分工

| 位置 | 性质 | 能否修改 |
| --- | --- | --- |
| 仓库根目录的 `README.md`、`SCORING.md`、`REPORT_TEMPLATE.md`、`docs/`、`selftest/`、`.gitignore` | 主办方原始文件 | **不修改**。主办方更新时整体替换 |
| `example/` | 主办方示例方案 | **不修改**，只用来对照 |
| `tasks/` | 示例题目和导入的 VerilogEval 题目 | 可以增加题目，不修改已有题目 |
| `AGENTS.md` | 给协作者和 AI 编程助手的简短指引 | 可以修改 |
| `43240-agent/`（除 `dev/`） | 参赛方案，会被提交 | 主要开发区 |
| `43240-agent/dev/` | 团队开发文档与测试脚本 | 不随方案提交 |

### 2.2 新文件放在哪里

- 方案运行时需要用到的（代码、提示词、技能、服务配置）→ `43240-agent/` 下对应目录
- 只在开发时使用的（测试脚本、分析工具）→ `43240-agent/dev/`
- 记录、笔记、分析 → `43240-agent/dev/` 下对应目录，见 2.3
- 拿不准时放 `dev/`：放错到 `dev/` 最多是少提交一个文件，放错到方案目录可能违反合规红线

### 2.3 dev/ 中各类文档的命名

| 目录 | 文件名格式 | 例子 |
| --- | --- | --- |
| `decisions/` | `<四位编号>-<主题>.md` | `0002-model-choice.md` |
| `notes/` | `YYYY-MM-DD-<主题>.md` | `2026-09-25-retry-strategy.md` |
| `experiments/` | 脚本自动生成：`YYYYMMDD-HHMMSS-<标签>.md` | `20260925-143000-veval-s5.md` |
| `failures/` | `<问题类型>.md` | `reset-polarity.md` |

主题部分用英文小写单词加连字符。

## 3. 文档写作

### 3.1 语言

- 正文用中文；目录名和文件名用英文
- `skill/*/SKILL.md` 的正文用英文，与 AMD 官方技能格式保持一致（见 `skill/README.md`）
- 代码注释的语言与所在文件已有的注释保持一致

### 3.2 表达

- **优先使用日常说法**，不要自己创造说法或缩写
- **专有名词和通用缩写保持原样**，不要强行翻译，例如 vLLM、SSH、GPU、API key、Vivado、
  git commit
- **含义不明显的缩写或术语，第一次出现时在后面加括号解释**，例如「L2（仿真结果与参考
  实现一致）」「pass@1（每题所有采样的平均得分）」
- 引用比赛规则时写清出处，例如「`SCORING.md` 第 2.9 条」，不要只写「2.9」

### 3.3 各文档写什么、什么时候更新

| 文档 | 写什么 | 什么时候更新 |
| --- | --- | --- |
| `43240-agent/README.md` | 方案现在的结构和行为：模块、流程、运行方式、环境变量、已知局限 | **改了代码结构或行为时，在同一个 commit 中更新** |
| `43240-agent/REPORT.md` | 为什么这样设计、实测效果、失败分析 | 阶段性节点；目前暂不编写 |
| `43240-agent/model/MODEL.md`、`manifest.json` | 模型、量化、上下文、推理服务的声明 | 模型或服务配置变化时，两者同时更新 |
| `dev/decisions/` | 重要决定及理由 | 做出或推翻决定时 |
| `dev/notes/` | 开发过程记录 | 随时 |
| `dev/experiments/` | 跑分记录 | 每次跑分后补写结论 |
| `dev/failures/` | 失败原因分析 | 分析完一类失败时 |

README 描述的是「现在」，REPORT 解释的是「为什么」和「效果如何」，同一内容不要两边
都写一遍，需要时互相引用。

### 3.4 写到数字时注明来源

文档中出现的得分、通过率、耗时等数字，要注明来自哪次运行（`dev/experiments/` 中的
运行编号），保证能追溯到对应的代码版本。

## 4. 提交与分支

### 4.1 格式

只写一行标题，不写正文，不加 `Co-Authored-By`：

```
<类型>(<范围>): <一句话说明做了什么>
```

- 用英文，动词原形开头，不加句号，尽量不超过 72 个字符
- `<范围>` 可以省略；需要时用目录名，例如 `agent`、`skill`、`serve`、`dev`
- 改动的原因需要长期留存时，写进 `dev/decisions/` 或 `dev/notes/`，不写在提交信息里

| 类型 | 用于 |
| --- | --- |
| `feat` | 新功能，如新工具、新技能、新的测试脚本 |
| `fix` | 修复错误 |
| `docs` | 只改文档 |
| `refactor` | 调整代码结构，不改变行为 |
| `test` | 测试、跑分相关 |
| `chore` | 杂项，如依赖、配置、恢复官方文件 |

例子：

```
feat(agent): patch previous attempt instead of regenerating on lint errors
docs(dev): record inference backend requirements
```

### 4.2 提交的粒度

- 一个 commit 只做一件事。代码改动和对应的 README 更新放在同一个 commit 中
- 提交前运行 `git status`，确认没有带上 `runs/`、`remote.env` 等不该提交的文件；
  创建 PR 前，再用 `git diff main...HEAD` 看一遍分支上的全部改动
- 改动了方案行为时，在提交前至少用示例题跑一遍（`LLM_BACKEND=mock ./run.sh ...`
  确认流程能跑通）

### 4.3 分支

`main` 是受保护的分支，**不直接向 `main` 提交或推送**。所有改动都在单独的分支上完成，
再通过 GitHub 的 PR 合并进 `main`。

**日常流程：**

1. 先切换到 `main` 并拉取最新代码，再从它新建一个分支
2. 在分支上修改、提交，可以提交多次，每个提交都要符合 4.1 节的格式
3. 把分支推送到 GitHub，创建一个 PR，PR 标题也按 4.1 节的格式写
4. 由另一名队员检查改动，有问题就在分支上继续修改并推送
5. 检查通过后，在 GitHub 网页上用默认的 **Create a merge commit** 合并：分支上的每个
   提交原样保留，并另外生成一个合并提交。合并提交的标题由 GitHub 自动生成
   （`Merge pull request #编号 ...`），保持原样即可，不需要符合 4.1 节的格式
6. 合并后删除这个分支（GitHub 网页上和本地都删），本地切回 `main` 并拉取最新代码

**分支命名：** `<类型>/<简短描述>`。类型沿用 4.1 节的提交类型，描述用英文小写单词加
连字符，例如 `feat/patch-repair`、`fix/interface-check`、`docs/conventions`。

**分支存在期间 `main` 有了新提交时：** 在 PR 页面点击 Update branch，或者在本地分支上
执行 `git merge main`，把 `main` 的新提交合并进来，解决冲突后再推送。不要用
`git rebase` 改写已经推送过的提交。

## 5. 代码约定

- **Shell 脚本**用 `set -eo pipefail`，**不要加 `-u`**：Vivado 的环境脚本引用了未定义的
  变量，加了 `-u` 会在读取 Vivado 环境时直接退出（见 `docs/API_CONTRACT.md` 第十节）
- **Vivado 临时文件**写在本地盘（`AGENT_TMP` / `EDA_TMP`，默认 `/tmp`），不要写在网络
  存储上；每次运行使用独立的工作目录
- **读取工具路径**时使用环境变量（如 `XILINX_VIVADO`），不要把安装路径写死
- **新增 Python 依赖**时同步写入 `requirements.txt`，因为比赛环境无法联网下载
- **不要让方案因异常而中断**：出错时写空的 `solution.v` 并在 trace 中记录原因，不要
  抛出异常退出
- **每一次模型调用和工具调用都要写入 trace**，这是评分要求
