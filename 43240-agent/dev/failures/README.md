**一类问题一个文件**，本文上半部分是**问题状态索引**（先看这里），下半部分是写作规则。

状态取值只有四种，含义固定：

| 状态 | 含义 | 读者该怎么用 |
| --- | --- | --- |
| **已解决** | 有可复现的方案，且验证过 | 照做即可 |
| **部分解决** | 一部分子问题已解决，其余仍未解决 | 看已解决与未解决两节 |
| **未解决** | 有明确的下一步，属于**待排期的活** | 看「可能的方案」 |
| **已确认受限** | 试过了、有确凿原因、**不再花时间** | 当结论用，别再重复尝试 |

## 每个文件的写法

```markdown
# <问题一句话>

| 项 | 内容 |
| 状态 | 已解决 / 部分解决 / 未解决 / 已确认受限 |
| 影响 | 哪些结论、哪次提交、哪个候选受影响 |
| 最后更新 | YYYY-MM-DD |
| 相关运行 | `20260928-…`（只列关键的那几个） |

## 问题
现象 + 判定到哪一级（L0 未通过 / L1 可编译失配 / L3 通过）+ 出现频率 + 影响范围

## 已解决
### <子问题>
现象 → 根因 → **具体方案（可直接复制的命令/配置）** → 怎么验证的 → 相关运行

（没有已解决的内容就写「（暂无）」，不要省掉这一节）

## 未解决
### <子问题>（待解决 / 已确认受限）
现象 → 已排除的可能 → **限制因素**（版本、硬件、许可）→ 可能的方案；已确认受限的写清原因

## 证据
指向 `../runs/<运行编号>/` 的日志与 trace
```

三条写作要求：

1. **只保留当前有效的结论**。被推翻的说法直接删掉（git 里找得回来），不要写
   「以前以为……现在改为……」；需要追溯时在 `decisions/` 的「变更记录」里指 commit。
2. **每个数字注明来源运行编号**（开发规范第 3.4 节），表格里也一样。
3. **状态变了就更新本文上半部分的索引**——索引与文件内容不一致，比没有索引更糟。

**这里可以引用参考答案，但这类内容绝对不能复制到 `skill/` 或 `agent/` 中**
（`SCORING.md` 第 2.9 条：预置答案会导致该赛道成绩作废）。技能包里只写适用于同类
问题的通用规律。
