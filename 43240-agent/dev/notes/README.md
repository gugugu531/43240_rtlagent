# notes/

开发过程记录。一天或一个主题一个文件，文件名 `YYYY-MM-DD-<主题>.md`。

记录做了什么、观察到了什么、下一步打算做什么。比较确定的结论（比如模型选择、重试策略的
取舍）稳定下来之后，整理进 `../../REPORT.md`；会影响方案设计的结论整理进 `../decisions/`。

## 两类文档要分开写

| 类型 | 例子 | 更新频率 | 写法 |
| --- | --- | --- | --- |
| **设计 / 口径** | [`2026-09-25-model-screening-plan.md`](2026-09-25-model-screening-plan.md)：取舍标准、硬门槛、候选清单、量化实验设计、指标定义、测试协议、预算 | 稳定，改动少 | 只写「我们打算怎么做」；做完之后不要在这里追加结果 |
| **进展 / 待办** | [`2026-09-25-screening-progress.md`](2026-09-25-screening-progress.md)：做到哪了、下一步做什么 | 滚动更新 | 按日期追加；做完的项就地标注结果与运行编号 |

分开的理由很直接：一份文档里混两种更新频率，改进展就得动设计文档，读者也分不清
哪句是「当初的设计」、哪句是「后来的结果」。

**结果数据**（分数、等级分布、耗时）不进这两类文档：能脚本生成的交给 `generated/`，
逐模型的观察写进 `2026-09-25-screening-results.md` 这类结果笔记。

## 子目录

| 路径 | 放什么 | 谁能改 |
| --- | --- | --- |
| `generated/` | **脚本生成**的对照表（如 `generated/2026-09-25-candidate-tables.md`，由 `dev/eval/overview.py` 产出） | **不要手改**——下次重跑会被覆盖。要改就改生成脚本 |
| `archive/` | 已被取代、只作备查的旧笔记 | 不再更新；引用时指向具体文件 |

## 命名与提交

- 文件名 `YYYY-MM-DD-<主题>.md`（主题用英文小写单词加连字符）
- 文档内的每个数字都要注明来源运行编号（开发规范第 3.4 节）
- 生成物的重跑命令写在它自己的抬头里，照抄即可更新
