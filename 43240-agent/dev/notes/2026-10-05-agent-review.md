## 审查结论

当前模块拆分已有基础，但求解仍依赖固定的「生成 → 接口检查 → lint → 综合 → 修复」循环。
控制器主要保存最新代码和上一条日志，缺少根据候选证据、失败类别、修复进展及预算决定下一步的机制。
原始模型信息不落盘，影响失败归因；组件虽然能单独测试，但还不能方便地通过配置替换和消融。
指定单题实验已经支持，不必为了这一能力重建评测系统。

本文记录已观察到的行为和证据，不表示这些问题已经解决。设计与实施计划单独维护。

## 求解架构问题

### 状态与候选选择

`solve_agent()` 中的 `best` 实际代表最新提取成功的候选。新候选在接口、lint 和综合之前就被
写入 `solution.v`；后续检查失败也不会恢复先前候选。

最小复现使用假模型和假工具：第一份代码接口、lint 通过，综合失败；第二份代码使用错误模块名，
接口检查失败；限制求解轮数后，最终仍输出第二份代码。这个复现证明存在候选退化路径，
不证明它在真实模型上的发生频率或得分损失。

候选已有 ID、来源、父候选和代码哈希，但检查证据主要写入 trace，没有成为候选选择的依据。
控制器也没有利用哈希识别完全相同的回复，可能重复执行工具检查。

### 功能反馈与停止条件

综合成功后立即接受候选。接口、lint 和综合不能判断状态转移、计数边界、复位行为或逐拍输出是否
符合题面；因此功能错误但工具检查通过的候选不会启动修复。

没有官方测试台是限制，但不排除从题面建立有限的行为检查。自生成测试通过和多候选行为一致
只能提供有限证据，不能标成官方 L2。内部 DUT 单独编译也不等同于官方带测试台的 L1 判定。

### 修复、错误路由与预算

- 修复提示要求局部修改、重复错误时换思路，但程序没有错误历史、修改范围或进展判断。
- 要求返回完整文件不等于模型必然重写逻辑；是否重写及是否导致退化需要候选差异和验证证据。
- 模型异常统一结束，尚未使用异常中的可重试信息；工具超时、代码失败和部分环境失败会进入相近的修复路径。
- 每阶段只检查剩余时间，综合可以使用几乎全部剩余预算；并非严格平均分配时间，也没有各阶段与后续修复的预留策略。
- 多草稿、目标模块缺失、疑似截断等提取诊断已经结构化，但控制流主要只判断 code 是否为空。
- 每轮只带上一份代码与上一条反馈；工具日志按固定关键词压缩，可能丢失源码位置及上下文。

### 技能机制

当前仅有接口技能。技能选择依赖签名字符串，首轮不注入，description 与 trigger 不参与路由；
多个命中按目录顺序取前面的技能。

已用内存样例核实：接口检查返回 `interface mismatch: port 'q' is 1 bits, must be 8 bits` 时
技能选择为空；输入 `VRFC 10-3180 cannot find port q` 时能选中接口技能。确定性接口检查与技能签名
没有完整衔接。

### 接口解析的最小复现

| 输入情形 | 当前结果 | 说明 |
| --- | --- | --- |
| 辅助模块 Helper 放在正确的 TopModule 前面 | 比较 Helper，报告模块名不符 | 解析器只读取第一个模块，没有按目标模块查找 |
| 接口参数 W 默认为 8，端口 `[W-1:0]`，候选使用 `[7:0]` | 报告位宽不符 | 解析器未计算默认参数，符号宽度与常数宽度被判为不同 |

提供 `interface.txt` 时上述结果会阻断后续检查；只从题面得到提示时，模块顺序问题可能产生错误建议。
参数例子只说明默认参数下宽度等价，不证明候选保留了完整参数化接口契约。

## 原始信息留存核实

| 信息 | 当前能力 |
| --- | --- |
| 每轮实际发送的完整 messages | 不保存 |
| 模型完整正文 | `LLMResult.text` 在内存中使用，不保存 |
| 模型原始响应 JSON | 不保存 |
| 服务端 reasoning 字段 | 解析后只保留是否存在的标志，没有保存内容 |
| 模型返回的 request ID、model 等字段 | 客户端有部分字段，主流程未完整写入 trace |
| 每轮提取后的候选代码 | `AGENT_SAVE_CANDIDATES=1` 时保存 |
| Agent 内部工具完整日志 | `AGENT_KEEP_WORK=1` 时保留工作目录与日志 |
| 最终代码与事件摘要 | 保存到 `solution.v` 和 `trace.jsonl` |
| 本地评测的判定结果和日志 | `run_eval.py` 保存；区别于 Agent 内部检查 |
| HTTP 请求中的候选产物 | 临时目录会删除，当前仅返回最终代码和 trace |

已有调试开关不能补回原始回复，无法可靠区分模型没生成、提取失败、选中草稿等原因。
`submit_client.py` 的 `response.json` 是投题耗时和传输状态摘要，不是模型原始响应。

## 模块化与实验粒度核实

现有模块可以导入并单独测试；流程测试用 `unittest.mock.patch` 替换工具链和技能加载。
模型客户端可以传入 `solve_agent()`，但工具链在内部创建，其他组件直接调用；没有统一配置入口
替换提取、技能、验证顺序、修复和选择策略。

`AGENT_MAX_ROUNDS=1` 可以限制轮数，但不能等同于官方 baseline，也不是其他模块的完整消融。

指定单题已有两种方式：

1. `./run.sh <单题目录> <输出目录>`：只求解这道题，内部检查按当前流程执行。
2. `run_eval.py --taskset <每行一个题名的文件>`：支持指定单题、多次采样、完整判定及汇总。

注意 `--tasks` 接收任务集合的父目录；`--limit 1` 只选排序后的第一道题；任务清单仍受排除列表
影响，需要时使用 `--no-exclude`。`--no-judge` 只求解，当前会提前返回，不生成后续分析、指标和总结。
HTTP 投题客户端没有同等的 `--taskset` 选项。

以下为后续可执行的单题命令，本文记录时没有运行完整模型评测：

```bash
cd 43240-agent
printf '%s\n' ex03_lfsr8 > /tmp/agent-one-task.txt
PYTHONDONTWRITEBYTECODE=1 AGENT_SAVE_CANDIDATES=1 AGENT_KEEP_WORK=1 \
  python3 dev/eval/run_eval.py --tag ex03-single \
  --taskset /tmp/agent-one-task.txt --modes agent --samples 3 \
  --jobs 1 --judge-jobs 1
```

该命令会写入 `dev/runs/` 和 `dev/experiments/`；工具和模型环境需要事先配置。

## 对既有实验结论的解释限制

`../failures/agent-repair.md` 等记录将部分 baseline 正确、agent 错误的最终对比归因于后续重写。
单凭这类最终对比不足以证明修复导致退化：首次生成的提示词、温度和独立采样也可能不同。
需要同一次 Agent 运行的前后候选及逐候选判定才能确认。

需要第三轮的题通常更难，第三轮最终正确率低也不能直接证明该轮没有边际收益。
必须比较继续修复、重新生成及提前停止，并控制任务、预算和采样条件。

本次只记录上述证据边界，不改写既有实验原始记录，也不把小样本现象当作新框架的收益承诺。
