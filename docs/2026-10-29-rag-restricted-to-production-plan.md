# 从 restricted 到旧 32 卡同等级运行的晋升方案

旧 32 张卡与新卡使用不同证据边界。旧卡是 `legacy_policy`：在真实编译／仿真诊断出现后，通过固定工具版本、错误码、源码结构和执行身份准入。新卡是 `restricted`：在首次生成前，仅根据公开题面判断是否提供一条窄方法。因此新卡不应改名为 `legacy_policy`；目标应是新增 `production_policy`（或单独的生产批准清单），表示默认配置可以自动使用，同时保留 `pre_generation` 阶段和公开合同谓词。

当前 rc4.5 的 28 张 restricted 已经是可用的显式开启版本。`config/rag97_pregen_bm25.yaml` 会实际注入，未知、冲突、不适用、资产异常和检索失败均返回空结果。它们还没有达到旧 32 张卡的稳定发布等级，因为默认配置尚未开启，当前每卡只有一到两个公开模型上下文，且没有生产流量 canary。

## 最快的生产化路径

第一阶段先使用 BM25 作为生产 canary 路由。BM25 不依赖 8020 服务，故障面更接近旧 32 卡；dense 保持 shadow，用于核对排名和服务健康。等 embedding 的重启恢复、并发和长时间稳定性通过后，再把 dense 或 hybrid 纳入生产候选。

每张卡进入生产批准清单前必须满足：

1. 当前版本和投影哈希固定，公开合同谓词已纳入实现哈希。
2. 至少三个互不相同的公开题面家族完成 control/card 配对；任何 card-only 退步立即阻断。
3. 每卡至少覆盖正向、方法已给出、冲突、信息不足、明确不适用、相邻主题和资产篡改；明确不适用必须得到 `not_needed`，不能只得到 `unknown`。
4. 冻结检索集上 BM25 top-5 召回通过；错误卡不得被最终接纳。dense 作为附加门禁，不作为第一阶段可用性的单点依赖。
5. 真实装配记录证明只发送一张卡、投影低于 1024 token、题面和接口未被改写。
6. 两台主机运行同一候选，完成至少 200 条混合 canary（含无关题面），错误注入为零；与关闭知识的对照相比无成功率下降。
7. 完成一次关闭 RAG 的回退演练；embedding 故障、超时、错误模型或非有限向量都必须返回空结果。

## 发布步骤

1. 冻结 rc4.5 的 28 张 restricted，不再一边修改谓词一边收集 canary。
2. 按 5–10 张组成生产候选 cohort，为每张补足三个独立上下文；优先选择已有不同上下文双臂证据的卡。
3. 在两台主机执行 BM25 on 的混合 canary；dense 同题只做 shadow 记录。
4. 审计实际请求、最终发送卡、模型输出和公开检查器，不用检索排名代替最终准入。
5. 通过的卡写入独立、哈希绑定的 `production-approval.json`，运行时只允许该清单中的卡在生产配置中自动注入。
6. 先发布显式的生产配置，观察一个完整工作窗口；确认无退步后再考虑替换默认配置。

按这个定义，restricted 到生产批准不是继续改 `activation_state` 字符串，而是补齐独立上下文、混合 canary、批准清单和回退证据。这样新卡能获得与旧 32 卡相同的“可默认使用”地位，同时不会伪装成诊断型旧策略。
