# 恢复链路与验证契约

本文描述当前 `design_verify_loop` 的恢复行为。目标是让故障发现、合法改动和新版本复检衔接起来；节点完成、模型同意或返回 HTTP 200 都不是功能正确的证据。

## 1. 恢复前确认能执行下一步

诊断归因为 RTL 或规划时，先检查下一稿额度与最低时间窗口。额度已满不再重建无人消费的计划；直接进入 `revise_plan` 也执行同一检查。检查器修订不消耗 RTL 轮次，可以在最后一稿上修订并复检。

候选自身缺少端口方向时，即使题面接口没有完整解析，也会报告明确的代码错误。功能编译错误按诊断文件与候选声明归因：只有绑定当前候选哈希、来源为候选且含具体诊断的 `code` 错误进入 RTL 修复。测试台、环境、混合或无法定位的错误不能凭 VRFC 编号推断为 RTL 错误。

规划评审用 `behavior_conflicts` 返回有公开引用的行为冲突。存在未解决冲突时，反馈给下一次规划；重试仍未解决则停止。无关命名选择不应列为行为冲突，空列表也不证明所有 `uncertain` 都已解决。

## 2. 接纳条件与实际执行一致

行为套件接纳前要求每个 case 有可比较输出。有效条件为假或掩码为零的输出不比较；实际启用比较范围内的期望位必须确定，有效条件及生效的掩码也不能未知。确定性预检失败会在模型复核与工具执行前返回，模型的 `accepted` 不能覆盖这个条件。

部分已知位在移位后继续保留。没有公开初值依据的状态仍为未知；只允许 `state.model_<signal>.initial={value,signal,quote}` 表示宿主能够识别、引用可核对的明确初始化。支持有限的 `initial q = 常量;` 和“使用 initial statement 初始化为常量”句式；复位值、假设、条件示例和未经支持的句式不能替代初值证据。

每个新行为 case 通过 `requirements` 列出本套件的要求 ID。每项声明要求必须有绑定且预期会比较的 case。该对应关系仅表示检查意图和可比较性，不证明测试足以覆盖语义。实际运行另记每个 case 的 `compared_samples/values/bits`；未知或零比较仍不能通过。

独立验收要求新增能够到达比较的输入与时钟历史及比较位。改 case 名称、仅增加不采样的尾部或只改变套件哈希不能算新增覆盖。已有小型组合输入域确实穷举时，保留原有穷举验收路径。

## 3. 使用小而明确的修复协议

初次构造仍返回 `status/suite`。检查器修订使用 `functional_suite_patch`，只返回 `{"replacements":{"获准信号":表达式}}`；宿主要求名称集合与诊断批准的集合一致，并合并到旧套件。端口、状态元数据、初值、输入序列、边沿、采样和比较域保持不变。补丁不能通过状态表达式间接关闭原比较。

合并后重新运行结构、引用、期望、覆盖与修订校验，再独立复核。套件换版后重新检查已编译候选；证据绑定实际候选、套件及检查器源码哈希。原样补丁和重复非法 JSON 都记录无进展并停止相同尝试，不修补字符串或放宽校验换取通过。

`unsupported` 先进入独立复核，区分能力缺口、规格不足与构造困难；构造困难或未获确认会返回构造纠错。确认 `unsupported` 前宿主必须核验公开引用；同一模型的复核仍可能误判，不能把它当作能力缺口的形式证明。

## 4. 按阶段累计辅助时间

`runtime.auxiliary` 默认如下，所有纠错请求共享所属阶段的累计额度：

| 字段 | 秒 | 范围 |
| --- | ---: | --- |
| `planning_s` | 150 | 初始规划与评审 |
| `building_s` | 240 | 初始套件构造、纠错和评审 |
| `acceptance_s` | 150 | 独立验收构造与评审 |
| `recovery_s` | 150 | 功能诊断、规划或检查器修订与评审 |
| `minimum_request_s` | 20 | 可用窗口小于此值不启动完整辅助请求 |
| `acceptance_reserve_s` | 60 | 已有候选时，为验收后的工具与恢复保留时间 |

其他辅助阶段沿用节点的后继预留，默认 120 秒。可用时间取阶段余额和整题剩余时间扣除后继预留的较小值；整题仍受 900 秒上限与收尾预留约束。模型发现、模板、分词与生成共享 chat 截止时间，晚到结果保存原始证据但不采用。HTTPX 的底层超时是每次 I/O 限时，整题硬截止仍由运行时负责；这些阈值是可调度策略，不是保证模型能在窗口内完成的预测。

## 5. 扩展时必须验证的过程

每个新恢复分支都要验证：明确故障 → 合法修复操作 → 产物真实变化 → 下游确实执行 → 结果绑定新版本。另测无额度、无时间、相同回复、无关字段变化、环境错误和错误反例。使用受控回复时说明模型选择是人为给定；原日志重放、本地工具验证与真实模型效果分别报告。不得使用官方答案、测试台或判定反馈回传求解。

## 6. 机制成立与真实效果分开报告

上述契约规定宿主如何接纳、路由和记录，不保证模型能生成合法检查器、正确归因或在额度内完成修复。模型复核可能误读表达式，也可能与后续诊断对同一题面给出不同解释；引用校验只能证明原文存在，不能证明模型的推论成立。预检只验证生成的期望能否确定地计算，不证明它符合题意。

初次构造及其纠错仍可能重写整份套件；第3节的受限表达式补丁只用于检查器修订。即使局部逻辑修改正确，完整响应格式无效时仍不会接纳。阶段额度和重试次数分别约束执行；整题尚有时间，不代表当前阶段还能继续。重复检测与重试次数同时耗尽时，应保留两个事实，不能假定重复检测额外减少了调用。

报告至少区分以下结果：

- 接口或编译错误被修正，且新候选通过对应工具复检。
- 功能检查实际发生采样和比较，记录差异及未知值；这仍不裁决生成期望的语义正确性。
- 检查器修订请求已发出、合法补丁已接纳、同一候选用新套件复检，分别记录。
- 工作流完成、内部功能检查通过与保存答案的官方成绩，分别报告。

较短工作流不执行某些检查时，其完成率不能与包含这些检查的工作流直接比较。评估恢复收益需要固定题目、请求策略和其他条件，核对实际产物变化、复检结果、调用及时间成本；没有受控对照时不作单一原因归因。实验数字、逐题证据和未实施的设计建议保存在仓库外的开发记录中。
